AI에게 시키는 사람은 많습니다.
AI 팀을 운영하는 사람은 드뭅니다.

여러 AI 에이전트에게 하나의 프로젝트를 맡기는 순간, 충돌·조용한 사고·책임 불명이 시작됩니다. 이 페이지는 한 사람이 실제로 AI 팀을 굴리는 방식을 그대로 공개합니다 — 가장 똑똑한 모델이 관리자로서 계획·배분·검수를 맡고, Codex가 실무자로 코드를 만들고, 서로 다른 회사의 모델이 서로의 결과를 검수하며, 사람에게는 중요한 결정만 옵니다.

2026년 10월 실제 운영 기준 · 모델은 바뀌어도 자리와 역할은 그대로 · GitHub 무료 요금제용 오픈소스 엔진(Apache-2.0) 포함

왜 필요한가

AI가 나빠서가 아닙니다. 규칙이 없어서 생기는 일입니다.

AI 에이전트 하나로 뭔가를 만들어 본 사람이라면, 두 개를 쓰기 시작한 순간 이 장면들을 만나게 됩니다.

"둘이 같은 파일을 고치고 있었다"

서로의 존재를 모르는 두 에이전트가 같은 곳을 수정합니다. 발견은 늘 한 시간 뒤, 수습은 당신 몫입니다.

"테스트를 '고친다'며 지웠다"

AI가 문제를 없애는 가장 빠른 길을 택했고, 그 변경은 이미 본선에 반영된 뒤에야 눈에 띄었습니다. 되돌릴 수 있을 때 잡았어야 합니다.

"밤새 바뀌었는데 누가 왜 했는지 모른다"

아침에 열어 보니 변경이 잔뜩. 어느 도구가, 어떤 세션에서, 무슨 근거로 했는지 아무 기록이 없습니다.

"완료됐다더니, 열어보니 미완성"

"다 됐습니다"라는 말과 실제 완료 사이의 간격 — AI와 일할 때 가장 비싼 간격입니다.

사람 팀도 규칙 없이 일하면 똑같이 됩니다. 회사가 직무 분담·결재·기록·검수로 사고를 막듯, AI 팀에도 같은 장치가 필요합니다. 여기 적힌 규율은 그 장치를 AI 팀에 옮긴 것입니다 — 일부는 GitHub가 서버에서 강제하고, 나머지는 모든 에이전트가 매 세션 읽는 규칙으로 지킵니다. 개발자가 아니어도 운영할 수 있도록.
팀 구성 — 누가 무엇을 하나

비싼 머리는 판단에, 부지런한 손은 실무에, 검수는 남의 눈으로.

한 모델에게 전부 시키지 않습니다. 회사처럼 자리를 나눕니다. 자리는 역할이고, 모델은 그 자리의 현재 주인입니다 — 새 세대가 나오면 주인만 바꿉니다.

오너 — 방향과 큰 결정만

사람 · 결정권자

무엇을 왜 만들지 정하고, 결과나 권한이 달라지는 결정만 내립니다. 결정은 열린 질문이 아니라 장단점이 붙은 2–4개 선택지로 받습니다. 가벼운 건 대화 안에서, 무거운 건 5분이면 읽히는 보고서형 질문지로 — 결정 카드는 많아야 세 장. 함께 설계하되, 코드는 직접 짜지 않습니다.

일을 쪼개고, 누구에게 맡길지 정하고, 위임 지시서를 쓰고, 검수 방법을 설계하고, '완료'를 판정합니다. 게으르고 똑똑한 관리자처럼 — 이 자리의 산출물은 코드가 아니라 지시서·결정·판정입니다. 큰 일은 워크플로우를 짜서 여러 하위 에이전트에게 나눠 돌리고 결과를 모읍니다.

검수석 — 정해진 모델 없음

만든 쪽 ≠ 검수하는 쪽

검수는 그 결과를 만들지 않은 새 좌석이 합니다. 가능하면 다른 회사의 모델로 — Claude가 만든 것은 Codex가, Codex가 만든 것은 Claude가 봅니다. 둘이 동의하면 확정, 엇갈리면 제3의 판정자나 사람에게 갑니다. 같은 회사 모델끼리의 합의는 '다양성'으로 치지 않습니다.

계획 자문 — 관리자가 둘

무거운 계획은 혼자 확정하지 않는 것이 원칙

규칙 변경·구조 설계·데이터 이전·보안 경계·되돌릴 수 없는 조치처럼 무거운 일은, 지휘석이 실행 전에 다른 회사 모델에게 계획을 자문받습니다. 자문역은 초안을 보기 전에 자기가 보는 위험과 대안부터 말하고, 깊게 한 번 봅니다. 채택·기각한 의견은 이유와 함께 기록하고, 중대한 이견이 풀리지 않으면 그 단계만 사람의 결정을 기다리며 나머지 일은 계속합니다. 자문역을 쓸 수 없을 땐 그 사실을 기록하고 진행하며, 자문한 좌석은 같은 작업의 검수자가 될 수 없습니다.

지휘석이 경로부터 선언한다

직접 할지, 누구에게 얼마나 깊이 맡길지를 먼저 한 줄로 적습니다(예: 'Codex · xhigh — 여러 파일 구현'). 무거운 계획이면 여기서 계획 자문을 받습니다.

실무석이 브랜치에서 만든다

지시서에는 바꿔도 되는 범위와 새 구성요소를 만들어도 되는지가 들어갑니다. 결과는 변경 제안(PR)으로만 올라오고, 정식 버전인 본선(main)에 직접 올리는 길은 서버가 막습니다.

다른 좌석이 검수한다

만든 적 없는 좌석이, 가능하면 다른 회사 모델로. 무엇을 봤고 무엇을 안 봤는지 — 검수 범위도 함께 적습니다.

GitHub가 조건을 확인하고 합친다

필수 검사가 모두 초록이고 리뷰 대화가 정리되면 자동으로 병합됩니다. 사람이 버튼을 누를 일이 없습니다.

지휘석이 영수증과 함께 보고한다

목표 대비 지금 어디인지 · 사람이 할 일이 있는지 · 다음 단계의 조건과 예상 시점 · 기다리는 결정. 세부 기록은 링크로.

배분 원칙

  • 고정 표가 없습니다. '이 일은 이 모델' 대신, 난이도·독립성·가용성을 보고 매번 배분합니다.
  • 하한선이 있습니다. 더 작은 모델은 사람이 그 작업에 지명할 때만 씁니다.
  • 몰래 바꾸지 않습니다. 요청한 모델이 실패하면 그 작업을 다른 모델로 자동 대체하지 않고, 보고한 뒤 결정을 기다립니다. 지휘석 자체가 멈추면 정해진 대체 절차로 지휘 업무만 이어 갑니다.
  • 같은 오류가 두 번이면 전략을 바꿉니다. 막힌 자원에 같은 호출을 반복하지 않습니다.
  • 폭이 필요할 때만 여럿을 띄웁니다. 다중 에이전트는 대화보다 약 15배의 토큰을 쓰고, 검수 단계까지 곱해지면 비용이 금방 불어납니다. 대규모 자동 팬아웃은 사람이 켤 때만.
작동 원리 — 네 가지 장치

기술이 아니라 규율입니다. 회사에서 이미 본 것들입니다.

처음엔 직접 만든 봇으로 구현했고, 지금은 대부분을 GitHub의 서버 규칙과 규칙 문서로 구현합니다. 도구는 바뀌어도 장치는 그대로입니다.

🚦

신호등 — 초록불 없이는 합쳐지지 않는다

GitHub 서버 규칙(ruleset) · 필수 검사 · 자동 병합

본선(main)에 직접 올리는 길은 막혀 있습니다. 모든 변경은 PR로 들어오고, 필수 검사가 모두 초록이고 리뷰 대화가 정리돼야 합쳐집니다. 강제 덮어쓰기와 본선 삭제는 금지, 예외 계정은 없음 — 모든 AI에게 똑같이. 조건이 갖춰지면 GitHub가 알아서 합칩니다. 판정을 GitHub 서버가 하므로, 감시 봇이 멈춰도 규칙은 그대로 서 있습니다.

결재 — 큰 건만 사람에게

두 질문 · 심각 목록 · 상시 위임

모든 일은 두 질문으로 가립니다: 되돌릴 수 있는가? 중요한 부분을 건드리는가? 되돌릴 수 없으면서 중요한 일, 그리고 미리 적어 둔 '심각 목록' — 되돌릴 수 없는 데이터 삭제, 약 100달러 이상의 지출과 새 금전 약정, 새 공개 서비스, 보안 경계 완화, 제3자 데이터·외부 소통·법무, 결과물 내용의 삭제·변경 — 만 실행 전에 사람의 승인을 받습니다. 서비스 배포는 앱마다 정해 둔 승인 정책을 따릅니다. '상시 위임'으로 등록된 앱의 통상 배포만 알아서 하고, 사용자 데이터가 걸린 앱처럼 '매번 승인'으로 지정됐거나 정책이 없는 앱은 먼저 묻습니다. 나머지는 상시 위임이되, 되돌릴 지점·기록·사후 검증이 의무입니다. 물어볼 필요 없는 걸 묻는 것도 규칙 위반이고, 한 번 명시적으로 승인한 일은 절차 끝까지 다시 묻지 않습니다.

이름표 — 모든 변경에 서명이 남는다

신원 서명 6종

어떤 도구가, 어떤 모델로, 어떤 작업 세션에서, 어느 기기에서, 어떤 작업 건으로 바꿨는지 — 그리고 공동 작성자까지, 여섯 줄 서명이 에이전트의 모든 변경에 붙습니다. 서명 검사를 필수 검사로 걸어 두면 서명 없는 에이전트 변경은 합쳐지지 않습니다 — 신원이 확인된 의존성 업데이트 봇의 원본 커밋만 예외입니다. "밤새 무슨 일이 있었나"가 아침에 다 읽힙니다.

영수증 — "했다"가 아니라 증빙이 남는다

완료 판정 · 검수 기록 · 실제 버전 대조

'완료'는 느낌이 아니라 판정입니다. 남은 검토가 0이거나 사람이 볼 목록으로 정리돼 있고, 실패한 항목까지 포함해 선언한 범위를 전부 대조했고, 무엇을 검증했고 무엇을 검증하지 않았는지 — 빠진 것과 승인을 기다리는 것까지 — 드러나 있어야 합니다. 데이터와 배포는 여기에 독립 검수를 통과한 영수증, 곧 검증 결과 파일과 수치가 더해져야 '완료'입니다. 배포는 실제로 떠 있는 버전과 기록을 대조하고, 어떤 모델이 일했는지 확인되지 않으면 추측하지 않고 '미확인'이라고 적습니다.

품질 헌법 — 열 가지 원칙

모든 에이전트가 따르는 열 가지 규칙

하나하나가 실제로 비용을 치른 사고에서 나왔습니다. 번호는 바꾸지 않습니다 — 규칙이 표류하지 않도록.

  • 1 · 거짓 완료 금지'다 됐다'는 선언한 범위 전체를 대조하고, 미검증·제외·승인 대기를 밝히고, 증빙을 붙일 때만 말한다.
  • 2 · 보존기능·데이터를 몰래 빼지 않는다. 구조를 바꾸면 전후 목록을 대조하고, 사용자 데이터 손실은 0.
  • 3 · 원천 우선, 전수 검증무엇이 정답의 원천인지 먼저 선언하고 전부 대조한다. 표본은 방법을 검증할 뿐, 완전성의 증거가 아니다.
  • 4 · 표면 분리사용자에게 보이는 화면에 개발 과정·인프라·모델의 흔적을 남기지 않는다.
  • 5 · 문구의 목소리자신 있고 명료하게. 단, 금융·법처럼 신뢰가 걸린 영역에서는 과장하지 않는다.
  • 6 · 모드 전환코드는 수술처럼 필요한 곳만, 문서는 꼼꼼하게, 데이터는 전수로.
  • 7 · 전달과 기록결과물은 정해진 위치와 형식으로. 관련 운영 문서의 갱신까지가 작업이다.
  • 8 · 승인 경계 — 양면심각한 것만 먼저 묻고 나머지는 맡긴다. 과잉 질문도 낭비다.
  • 9 · 독립 검증만든 쪽과 검수하는 쪽을 나누고, 가능하면 다른 회사 모델로. 합의가 곧 확정이고, 엇갈리면 몰래 한쪽을 고르지 않는다.
  • 10 · 낭비 금지검증된 환경 사실은 실패나 변화의 징후가 없으면 다시 재지 않는다. 유료 재실행 전에는 같은 작업이 이미 돌았는지부터 본다.
일하는 습관

당신의 방식대로

같은 도구라도 쓰는 사람의 방식은 다 다릅니다. 업무 취향과 규칙을 한 곳에 적어 두면, 모든 에이전트가 그것을 읽고 따릅니다 — 규칙 요약본은 매 세션, 취향 원장은 관련 결정을 내리기 전에.

  • 말하는 언어보고서·대화 모두 당신의 언어로
  • 보고 스타일결론부터 한 줄로? 자세한 서술로?
  • 결정을 받는 방식열린 질문 대신, 장단점이 붙은 2–4개 선택지 메뉴로

  • 조용한 시간밤에는 알림 대신 아침 보고로
  • 취향 원장에이전트에게 반복해서 시키던 말, 말한 그날 한 줄씩 적어두면 끝 — 이후 모든 에이전트가 따릅니다
  • 작업 시트데이터·제품·문서·루틴·조사·규칙 — 일의 종류마다 관문과 완료 기준이 다른 시트 6종

신호등 켜기

개인 계정의 비공개 저장소라면 월 4달러짜리 GitHub Pro, 조직 소유라면 Team 이상의 요금제가 필요하고, 공개 저장소는 무료로도 됩니다. 저장소마다 서버 규칙을 겁니다 — 변경 제안(PR) 필수 · 사람 승인 0건 · 리뷰 대화 정리 필수 · GitHub Actions가 낸 필수 검사 통과 · squash 병합 · 직선 이력 · 강제 덮어쓰기와 본선 삭제 금지 · 예외 계정 없음 · 자동 병합. 혼자 운영하면 자기 PR을 스스로 승인할 수 없으니 사람 승인 대신 검사로 막고, 검사가 아직 없는 저장소도 PR 필수부터 겁니다. squash는 변경 묶음을 한 줄의 기록으로 합치는 방식입니다. 설정은 에이전트가, 결제는 사람이.

정직한 상태 표시

되는 것과 안 되는 것

신뢰를 다루는 방식이 스스로 과장하면 그걸로 끝입니다. 어떤 규칙이 기계로 강제되고, 어떤 규칙이 약속으로 지켜지는지 구분해 적습니다.

✓ 기계가 강제합니다

  • 본선 보호 — PR 필수·필수 검사·리뷰 대화 정리·squash·직선 이력·강제 덮어쓰기와 본선 삭제 금지 (GitHub 서버 규칙)
  • 서명 검사 — 필수 검사로 걸어 둔 저장소에서는 서명 여섯 줄이 빠진 에이전트 변경은 병합 불가
  • Codex 호출 — 정해진 연결 스크립트를 거치면 모델 고정, 생각의 깊이를 지정하지 않으면 실행 거부, 호출마다 영수증. 스크립트를 우회한 호출은 기계로 막지 못하고 감사로 찾아냅니다
  • 유료 배치 중복 방지 — 같은 요청을 다시 제출하려 하면 실행기가 막음 (Anthropic 배치)
  • 모델 등록부 — 모델 이름은 등록부 한 곳에만. 퇴역한 모델 이름이 규칙 문서에 다시 들어오면 검사가 막음

◐ 규율로 지킵니다 (기계 강제 아님)

  • 만든 쪽 ≠ 검수 쪽, 계획 자문, 비례성 — 규칙과 스킬이 안내할 뿐, 위반을 기계가 막지는 않습니다
  • 실제로 어떤 모델이 일했는지 — 대부분 '요청한 모델'까지만 기록됩니다. 실행 신원이 보이지 않으면 '미확인'으로 적고, 추측으로 채우지 않습니다
  • 무엇이 '심각'인지의 판단 — 목록은 글로 정해져 있지만, 적용은 지휘석의 판단입니다
  • 규칙이 실제로 작동하는지 — 약 90일마다 사람이 직접 시작하는 감사로 확인합니다. 문서에 있다고 작동한다고 믿지 않습니다

− 아직 안 됩니다 (숨기지 않습니다)

  • 규칙 변경의 즉시 전파 — 이미 열린 세션에는 바로 닿지 않을 수 있습니다. 각 기기에 최신 규칙을 내려받아 적용·대조한 뒤, 새 세션부터 반영됩니다
  • 문서끼리의 일관성 검사 — 검사는 돌고 있지만 아직 관찰 단계라, 어긋나도 병합을 막지는 않습니다
  • 현 세대 Opus의 배치 처리 — 호환성 확인이 끝날 때까지 새 제출을 멈춰 두었습니다. 그동안은 여러 일꾼을 동시에 띄워 처리합니다
  • 검사 정의 자체의 물리적 보증 — 아래 '경계' 참고
⚖️ 경계도 분명히 합니다: 신호등은 정책이지, 코드가 안전하다는 증명이 아닙니다. 서명이 있고 검사가 초록인 변경은 합쳐집니다 — 그 검사가 충분한지, 그 코드가 옳은지는 신호등이 판단하지 않습니다. 같은 저장소 안에서 검사 정의 자체를 바꾸는 변경까지 서버 규칙만으로 물리적으로 막지는 못하므로, 민감한 경로는 만든 쪽과 분리된 검수자를 절차로 둡니다. 좋은 검사를 붙이는 일은 여전히 당신과 당신의 에이전트의 몫입니다.

  • 신호등(머지 게이트) — 라벨·검사·최신성·서명 확인 후에만 병합
  • 결재함 — 중요 결정만 이슈로 도착, 👍 또는 /approve로 응답

  • 사고 병합 자동 되돌리기 — 봇이 되돌림 PR을 만들어 제안(옵트인, 그 PR도 신호등을 통과해야 합침)
  • 개념 문서 9종 전부 한국어 미러 제공(충돌 시 영문이 정본)
  • 설치 점검 리포트(verify-setup) — 배포된 게이트를 언제든 재검증하고, 조용히 죽은 크론도 보이게 만듭니다
  • 결재함 리마인더 — 정한 시간이 지나면 한 번 알리고, 외출 시간 동안은 시계를 멈췄다가 복귀하면 요약을 한 번 보냅니다(v1.4, 옵트인)
  • 완료 영수증 검사 — 등록부·본선 최신 커밋·버전 선언을 정확한 커밋 단위로 묶어 대조합니다(v1.5; 완료를 '승인'하지는 않습니다)

비슷해 보이는 도구들과의 관계

도구 하는 일 이 프로토콜과의 관계
AI 오케스트레이터 (AI Maestro 등) 여러 에이전트 세션을 띄우고 서로 대화하게 함 보완 — 그쪽은 에이전트를 "일하게" 하고, 우리는 그 일이 "합쳐질 자격"을 지킵니다. 같이 쓰면 좋습니다
CI (GitHub Actions의 테스트 등) 코드 검사를 실행 보완 — 우리는 그 결과를 병합 조건으로 소비합니다. 검사는 당신 것, 신호등은 우리 것
GitHub Pro 서버 규칙 (ruleset) 내장 병합 보호 — 비공개 저장소는 유료 지금의 기본값 — 결제가 가능하다면 이쪽이 더 단순하고 단단해서, 이 규율도 여기로 옮겼습니다. 에이전트 신원은 서명 필수 검사로, 결재는 승인 경계 규칙으로 보탭니다
